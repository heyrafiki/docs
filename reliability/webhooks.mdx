---
title: "Webhook reliability"
description: "Accept delayed, duplicate and out-of-order events without duplicating effects."
---

Webhook delivery is asynchronous evidence. It may arrive late, more than once or in a different order from the provider request.

## Consumer contract

Every Webhook consumer must:

1. verify the provider signature against the unmodified request body;
2. reject unsupported event versions;
3. record the provider event ID in a durable inbox;
4. acknowledge only after durable acceptance;
5. apply the event idempotently;
6. validate the requested state transition;
7. retry transient failures with bounded backoff;
8. move exhausted work into a reviewable state;
9. reconcile critical operations with the provider.

## Duplicate delivery

A repeated event returns success after the consumer confirms that its inbox already contains the event ID. The handler must not repeat the business effect.

## Ordering

Do not assume creation, success and reversal events arrive in sequence. Compare the event to the current authoritative state, reject invalid transitions and retain enough evidence for reconciliation.

## Unknown outcomes

A lost provider response leaves the original operation in `confirming`. A later Webhook, provider query or reconciliation job resolves that operation through the same stable reference.

## Public event reference

Heyrafiki will publish event names, envelopes, signature instructions, retry schedules and examples when the Webhook specification is authoritative. This page records the reliability contract without inventing endpoint details.
