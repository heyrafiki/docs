title: "Versioning and compatibility"
description: "Review the compatibility rules planned for public Heyrafiki interfaces."
---

Public interfaces need explicit versions and migration paths. A documentation edit does not create or change a supported contract by itself.

## Interface authorities

| Interface | Version source |
| --- | --- |
| API | OpenAPI document and API release |
| Webhook | Event type and schema version |
| SDK or Package | Package version and release tag |
| MCP tool | Tool schema version |
| Self-hosted component | Component release and migration guide |

## Compatibility rules

- Additive optional fields are compatible unless their semantics change existing behavior.
- Required fields, removed fields and changed meanings require a new contract version.
- Consumers must ignore documented unknown optional fields where the contract allows it.
- Webhook consumers must handle delayed events from supported older schema versions.
- Security fixes may shorten a support window when continued operation would be unsafe.

## Deprecation

A deprecation notice will identify the affected interface, replacement, migration steps, support window and final removal date. Deprecated content remains clearly marked until the supported window closes, then redirects to the current path where appropriate.

## Package releases

SDKs and Packages will use semantic versioning when their public contracts are stable. Examples pin a tested version. Generated reference pages come from the same release source as the implementation.

## Current status

No public API, SDK, Webhook catalogue, MCP tool set or self-hosted release is currently declared stable. The [builder overview](/builders/overview) records the available surface.
